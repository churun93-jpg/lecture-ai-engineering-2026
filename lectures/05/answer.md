- 検索だけを実行して見つかったページと、その本文で確認できたこと：
  `uv run python -m app.retrieval "LoRA QLoRA 違い"` を実行すると、1位に第2回 p.52「LoRA と QLoRA：大きなモデルも GPU 1 台で調整できる」、2位に p.51「PEFT：モデル全体ではなく、一部だけを学習する」、3位に p.60、4位に p.47、5位に p.61 が返った。1位の p.52 と 2位の p.51 の本文に「元の重みは固定し、小さな『差分』（小さな行列A・B）だけを学習する（LoRA）」「さらに元の重みを4bitに圧縮する（QLoRA）」という直接の根拠が記載されている一方、3〜5位（p.60, p.47, p.61）は同じ用語（LoRA / QLoRA）を含むものの、演習手順やRAGとの比較に関するページであることを確認できた。
- `--trace`で見えたツール呼び出し（ツール名・引数・回数、Treeでたどった目次など）：
  - **ベクトル検索**：`search_materials({'query': 'LoRA 何を固定 学習 QLoRA 何を加える'})` を 1回呼び出した。
  - **Tree**：`browse_tree` を計4回呼び出し、「資料一覧（`{}`）」→「基盤モデルの仕組み（`lec02-main`）」→「選んだモデルを、いつ・どう直すか（`lec02-main-s045`）」→「LoRA と QLoRA（`lec02-main-p052`、本文717文字取得）」の順で目次階層をたどった（モデル応答は計5回）。
  - **Graph**：`search_graph({'query': 'LoRA 固定 学習 QLoRA 追加 第2回'})` を 1回呼び出し、`lec02-main-p052` などを入口（seeds）として前後ページや共通用語ノードから候補（expanded）を取得した。
- 取得した情報が足りなかった例、取得できたのに回答へ使えなかった例：
  今回の質問は単一ページ（第2回 p.52、および概要の p.51）で根拠が完結していたため、どの方式でも情報不足にはならなかった。一方で、ベクトル検索の上位3〜5位（p.60, p.47, p.61）は質問の直接の答えには不要なページであり、Graph探索では周辺ページ（p.53, p.61）まで取得した結果、質問で聞かれていない演習のヒントまで回答末尾に付加された。また、Tree探索では途中の目次候補ではページの先頭文しか見られないため、見出しだけで判断して p.52 のみを読み、p.51 の全文は取得しなかった（ただし p.52 だけで根拠は十分そろっていた）。
- 今回の用途に採用したい方式と、その理由・比較条件の限界：
  - **採用したい方式と理由**：**ベクトル検索（基本RAG）**（または複数ページの関連知識が必要な場合は **Graph**）。全文投入と比べると入力トークン数が `117,025` → `3,032`（約1/38）、推定コストが `$0.029447` → `$0.001134`（約1/26）と圧倒的に低く、Tree（9.57秒・モデル応答5回）のように階層ごとにモデルを往復させる待ち時間もないため、速度・コスト・根拠の正確さのバランスが最も優れている。
  - **比較条件の限界**：現状では全文投入のみ全9資料・438ページを対象としており、他方式（第1〜3回本講義・214ページ）と対象範囲が異なっている点、また単一ページで答えがそろう質問1問での比較であるため、章をまたぐ質問や資料に答えがない質問も含めて同じ対象資料で比較する必要がある。
- 気づき・疑問：
  全文投入でも `gemini-3.1-flash-lite` は3.38秒で正確に p.52 を見つけて回答できたが、1問あたり約11.7万トークン（約$0.03）を消費するため、質問回数が増える実運用ではRAGによる絞り込みが不可欠だと実感した。また、TreeはDB不要で人間のように目次をたどれる反面、階層を深掘りするたびにツール呼び出し（往復）が発生して時間とトークンが増えるというトレードオフが明確に分かった。

- 比較した質問と、固定した条件（モデル・対象資料など）：

  - 対象資料：第1〜3回本講義・214ページ（`data/rag_data/index.sqlite3`、固定）
- 結果（変更前後の回答・根拠、`--trace`の出力、時間・トークン数・生成API推定費用など）：
  - **変更前（`RAG_TOP_K = 5`）**：
    - ツール呼び出し：`search_materials({'query': 'LoRA 何を固定 学習 QLoRA 何を加える'})`（1回）

    - 時間・トークン・費用：`4.15 秒` / 入力 `3,032 tokens`・出力 `251 tokens`（モデル応答 2回） / `$0.001134 USD`
  - **変更後（`RAG_TOP_K = 2`）**：
    - ツール呼び出し：`search_materials({'query': 'LoRA 固定 学習 QLoRA 追加'})`（1回）

- 改善した例と、残る失敗・制約：
  - **改善した点**：STEP 2で確認した通り、この質問では上位2件（p.52, p.51）に核心の根拠が集中しており、3〜5位（p.60, p.47, p.61）は周辺話題だったため、`RAG_TOP_K = 2` に絞ったことで回答の正確さと引用根拠（p.51, p.52）を維持したまま、**入力トークン数を 3,032 → 1,742 tokens（約43%減）、生成API推定費用を $0.001134 → $0.000754 USD（約34%減）** に削減できた。
  - **残る失敗・制約**：単一ページ（または2ページ）で完結する質問では `RAG_TOP_K = 2` が効率的だが、3ページ以上に根拠が分散する複数ページ型の質問や、ベクトル検索の1〜2位に似た用語の別ページが来てしまい3位以下に本当の根拠がある場合には、必要な根拠を取りこぼすリスクが高まる。また、実行時間はAPIサーバーの混雑状況によって `4.15 秒` → `12.79 秒` のように揺らぐため、1回の計測だけで速度の優劣は判断できない。
- 気づき・疑問：
  検索件数（`RAG_TOP_K`）は多ければ良いというわけではなく、増やしすぎると無関係なページまでプロンプトに入ってトークンとコストが増え（場合によってはノイズになる）、減らしすぎると根拠の取りこぼしにつながるため、扱う質問が「単一ページで完結するか」「複数ページにまたがるか」に応じて調整すべきパラメータであると分かった。
